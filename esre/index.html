Especificación de requisitos de software

Guía de estudio · IEEE 29148

Cómo redactar un buen requisito

Esta guía aplica de forma didáctica principios de ISO/IEC/IEEE 29148 para especificar necesidades de manera identificable, clara, necesaria, viable, verificable y trazable. La prioridad y el método de verificación permiten tomar decisiones y comprobar el resultado.

Requisito funcional

Describe una capacidad del sistema: qué debe hacer para un usuario o actor.

No funcional

Describe una cualidad o restricción: rendimiento, seguridad, accesibilidad o compatibilidad.

Historia de usuario

Expresa una necesidad desde la perspectiva del usuario y se complementa con criterios de aceptación.

Funcional

Qué debe hacer el sistema

Redáctalo como una capacidad observable. Nombra el sujeto, una acción y, si corresponde, la condición o información involucrada.

El sistema deberá permitir que el cliente consulte los turnos disponibles por servicio y fecha.

Evita: “La aplicación tendrá turnos”. No indica quién hace qué ni permite verificar el resultado.

No funcional

Con qué calidad o restricción

Define una cualidad medible y el contexto de evaluación: métrica, umbral, condición y, cuando aplique, población o carga.

El sistema deberá mostrar disponibilidad en menos de 2 s para el 95 % de 50 consultas simultáneas.

Evita: “La aplicación debe ser rápida”. “Rápida” es ambiguo y no se puede comprobar.

Lista de verificación

Antes de agregar un requisito

  • Identificable: tiene un ID único y un tipo definido.
  • Claro y sin ambigüedad: una persona diferente puede interpretarlo de la misma forma.
  • Completo y consistente: incluye la información necesaria y no contradice a otro requisito.
  • Necesario y viable: aporta valor y puede realizarse con las restricciones del proyecto.
  • Verificable: se puede demostrar con prueba, inspección, análisis o demostración.
  • Trazable: conserva su fuente, prioridad, criterio de aceptación y relación con la validación.
Profundizar: criterios de aceptación, MoSCoW y trazabilidad
Criterio de aceptación

Indica la evidencia para aceptar el requisito. Una forma útil es: Dado un contexto, cuando ocurre una acción, entonces se observa un resultado.

Must / Should

Must es imprescindible para entregar valor mínimo. Should es importante, pero puede postergarse si existe una alternativa.

Could / Won't

Could aporta valor si hay capacidad. Won't deja explícitamente un requisito fuera del alcance de esta versión.

Trazabilidad

El ID, la fuente, el criterio de aceptación y el método de verificación conectan una necesidad con su validación posterior.

Profundización · Construcción de requisitos

Del enunciado informal al requisito bien formado

La referencia local ISO/IEC/IEEE 29148:2011 distingue el requisito de una intención, una decisión de diseño o una simple descripción. Un requisito expresa una necesidad del sistema que puede comprobarse bajo condiciones y límites definidos.

Patrón de redacción

[Condición] [Sujeto] deberá [Acción] [Objeto] [Restricción medible]

Ejemplo: Cuando el cliente confirme una reserva, el sistema deberá registrar la operación y mostrar un comprobante en menos de 2 segundos.

Para cada requisito

Calidad individual

  • Necesario: si se elimina, queda una necesidad sin cubrir.
  • Independiente de implementación: expresa qué se necesita, no la solución técnica elegida.
  • No ambiguo, completo y singular: se interpreta de una forma, aporta datos suficientes y expresa una sola obligación.
  • Factible: puede realizarse dentro de las restricciones técnicas, legales, de costo y plazo.
  • Verificable y trazable: admite evidencia y se vincula a su fuente, diseño y prueba.

Para el documento completo

Calidad del conjunto

  • Completo: cubre el alcance sin elementos pendientes por definir.
  • Consistente: no contiene contradicciones, duplicados ni términos usados con sentidos distintos.
  • Acotado: mantiene el alcance acordado y evita el crecimiento no controlado de requisitos.
  • Abordable: puede satisfacerse con los recursos y restricciones del ciclo de vida.
  • Priorizado: MoSCoW ayuda a ordenar el valor, pero no reemplaza los criterios de calidad anteriores.

Lenguaje a revisar

Palabras que requieren precisión

Reemplaza términos subjetivos o abiertos como “rápido”, “fácil de usar”, “mejor”, “significativo”, “si es posible” o “como mínimo” por una métrica, una condición y un umbral. Documenta también supuestos y restricciones; si una tecnología concreta es obligatoria, declárala como restricción de diseño, no como una funcionalidad.

Historias de usuario

Una necesidad, no una solución

La estructura “Como [rol], quiero [objetivo], para [beneficio]” comunica valor desde la perspectiva de quien usa el producto. No reemplaza al requisito funcional: se complementa con criterios de aceptación verificables.

Método de verificación

Cómo se reunirá evidencia

Prueba ejecuta el sistema; inspección revisa un artefacto o configuración; demostración observa el comportamiento en uso; y análisis evalúa datos, modelos o cálculos. Elige el que permita demostrar el criterio.

Fuente

De dónde surge la necesidad

Registra la persona, área, normativa, investigación o documento que motivó el elemento. La fuente permite validar el requisito con quien lo necesita y mantener trazabilidad cuando cambia.
